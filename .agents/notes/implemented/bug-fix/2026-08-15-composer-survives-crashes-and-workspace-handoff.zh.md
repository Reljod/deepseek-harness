# Agent Note: The composer survives entry crashes and the workspace handoff

Status: implemented

[English](2026-08-15-composer-survives-crashes-and-workspace-handoff.md) | 中文

## 问题

两个缺陷都会让 Web 输入框停止接受输入，在用户看来都是"我打的字没有出现"。

从 hero 工作区按钮选择工作区会冻结草稿。选择会执行 `selectWorkspace`：连接工作区、把草稿迁移到落地的会话、再打开该会话；在此期间选择列表在指针下卸载，焦点因而落回文档。选择之后的每一次按键都没有落到任何可编辑节点上；又因为输入框的字形来自一层背景层，其上的 textarea 是 `color: transparent`，所以框里一直显示选择之前的草稿。用户先打一个字符、选择工作区、继续打字，看到的就只有那第一个字符，然后把它发了出去——一份生产会话日志记录的用户消息正是 `"C"`。

另一个缺陷是：输入框内部的任何渲染错误都会永久移除输入框。`SlotCore.reportEntryError` 会把崩溃的条目从其单元格中退役，且该退役永不过期；于是只有一个注册的 `single` 类单元格——`conversation.composer.bar` 正是如此——就此枯竭，在整个页面生命周期内只渲染一个空的 `<div data-slot-error>`。hero 标题与工作区行是输入框的同级节点、仍在渲染，所以窗口看起来正常，只是输入卡片消失了，而草稿不重新加载页面就找不回来。

## 决策

**退役必须有后继者。** 只有当同一单元格中还有其他存活条目时，`reportEntryError` 才让崩溃条目退役。退役是一种向下回退，没有可回退对象的单元格从中得不到任何好处，却会永久失去自己的界面。独占单元格的崩溃条目保留在原位，其崩溃仅限于边界内部。

**输入发生变化时，崩溃条目获得再次渲染的机会。** `SlotErrorBoundary` 接受 `retryToken`，并在该令牌变化时清除失败状态。session-maybe 条目传入当前会话 id，因为它们刻意在会话切换时不重新挂载——输入框要在 hero 与停靠形态之间保留同一个 textarea——若不如此，崩溃就会比引发它的全部输入活得更久。root 条目不传令牌，保持锁定直到重新挂载。

**输入框把"有 id 但无绑定"的会话渲染为无会话状态。** 该条目的 inject 过去通过 `InputHub.shell` 解析输入外壳，而该方法在会话没有绑定时抛错。这个 inject 运行在条目的错误边界内，因此抛错成了生命周期竞态删除唯一输入框注册的途径。`InputHub.maybeShell` 改为返回 `undefined`，inject 走它本就具备的"当前无会话"分支。仍然存活却丢失了 `conversation` 服务的会话作用域依旧大声失败：那是接线错误的树，而非被拆除的会话。

**工作区交接会取回焦点。** `ui-conversation` 持有一个 `FocusClaim`：`selectWorkspace` 发起一个指名草稿所迁往会话的认领，该会话的输入框取回焦点并把光标置于草稿末尾。认领指名会话，是因为输入框会在它所跟随的那次切换中重新挂载——以挂载时刻为基线会让新实例把已发起的认领当成旧的。认领会跨越交接所需的数次渲染（迁出草稿、迁入会话的空草稿、随后是承接的值，每一次都会让光标重新塌缩），并在承接草稿落地或用户开始输入时（以先发生者为准）结束。

认领存放在插件 fiber 上而非 `ConversationRoot` 中，因为常驻骨架会在它所要通知的那次会话切换中重新挂载，组件状态会在输入框看到它之前被重置。

## 备选方案

**保留抛错，交给边界捕获。** 抛错正是输入框消失的原因。`session-maybe` 插槽声明自己在有无会话时都能渲染，因此其 inject 必须容忍它所声明的这种缺失；在此处大声失败会把一次瞬时的生命周期竞态变成永久不可用的应用。

**用定时器让退役过期，或在每次渲染时重试崩溃条目。** 两者都会重新引入永久退役所要防止的崩溃循环。把重试绑定到条目输入的变化，可以让恢复被用户驱动的事件所限定。

**按会话重新挂载输入框（用会话 id 作为边界的 key）。** 这确实能清除崩溃，但也会在 hero 与输入框形态切换时销毁 textarea，而 session-maybe 的接管契约正是为防止这一点而存在。在不重新挂载子树的前提下重置边界状态，可同时保住两项性质。

**把焦点认领作为组件状态放在 `ConversationRoot` 中。** 先这样做过并实测：骨架会在工作区切换时重新挂载，所以被抬升的令牌在输入框渲染前就消失了，光标停在 0，输入被插到承接草稿之前。

**切换后重读迁出草稿以捕获迟到的按键。** 交接窗口依然存在——同一 tick 内落到迁出外壳的按键会被丢弃。恢复焦点消除了会丢失其后每一次按键的情形；追逐残余的亚帧窗口需要两阶段草稿转移，其复杂度没有现有报告能够证成。

## 测试

`packages/client/ui-slots/tests/core.client.spec.ts` 覆盖退役策略：有后继者时退役、独占条目保留、部分退役单元格保留最后一个存活者、list 单元格按 id 判定、chain 条目永不退役。`packages/client/web-react/tests/scoped-slots.client.spec.tsx` 证明：为某个会话崩溃的 session-maybe 条目会在下一个会话重新渲染，而不是锁定崩溃面；其伪 host 同步了账本策略。`packages/client/ui-conversation/tests/apply-inject.client.spec.tsx` 固定了这一行为：输入框 inject 对无绑定会话返回无会话面，而缺少服务的存活作用域仍然抛错。`packages/client/ui-conversation/tests/input-bar.client.spec.tsx` 覆盖认领：焦点与草稿末尾光标、忽略他会话的认领、响应本实例挂载前发起的认领、跨越交接渲染保持、输入时释放，以及绝不把焦点抢入已锁定的输入框。

## 影响

输入框中的渲染错误现在的代价是一次崩溃面，并由下一次会话切换清除，而不再是一个无法打字的应用。代价是：真正损坏的条目会重试而非保持退役，因此确定性崩溃会在每次会话切换时重现一次并各记录一次日志。

`ComposerFocusClaim` 为输入框的 hooks 隔间新增了一个成员，因此每个构造这些 props 的测试替身都要提供它。

输入框的字形来自透明 textarea 之上的背景层。今后任何让已发布草稿停滞、而 DOM 仍接受输入的缺陷，都会表现为不可见的文字而非失效的控件——这正是最初那些报告难以解读的原因。
